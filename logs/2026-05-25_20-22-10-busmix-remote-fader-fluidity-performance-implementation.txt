BusMix remote fader fluidity performance implementation
Timestamp: 2026-05-25_20-22-10

Context
-------
- User reported that `remote-fader-subscription-sync` works correctly against the real console, but remote fader movement has perceptible delay and can become visually frantic before settling.
- Goal: keep the app performant on modest devices and avoid replaying delayed network history.

Implemented
-----------
- Added a BusMix-specific fader subscription time factor:
  - `X32Protocol.defaultBusMixFaderSubscriptionTimeFactor = 20`
  - `BusMixService.subscribeChannelLevelUpdates(...)` now passes this value to `OscClient.subscribeScalarValue(...)`.
- Added `remoteFaderCoalescing`:
  - keeps only the latest remote fader value per path before a frame flush;
  - drops duplicate values within epsilon;
  - drops out-of-order packets;
  - supports stale local echo suppression windows;
  - exposes ref-friendly cumulative stats.
- Added `faderSubscriptionScope`:
  - visible faders subscribe immediately;
  - recently visible faders are retained briefly;
  - retained subscriptions are capped to a small buffer instead of expanding to all 48 faders.
- Updated `useBusMixRemoteFaderSubscription`:
  - buffers remote subscribed fader values in refs;
  - applies values with `requestAnimationFrame`;
  - cancels pending frame work during cleanup;
  - emits diagnostics for incoming packets and frame flushes without React state per packet.
- Updated `useBusMix`:
  - added batched remote fader reconciliation through one store update per frame;
  - preserved linked-channel visual reflection through `applyLinkedRemoteLevelUpdates(...)`;
  - added local echo suppression timestamps for recently changed local faders and linked peers;
  - extended `getRealtimeSubscriptionHealth()` with performance counters/rates.
- Added tests for:
  - remote fader coalescing;
  - subscription scope hysteresis/capping;
  - linked remote batch updates;
  - BusMix fader subscription time factor.
